**모델별 결과 요약**

GPT: 입력 내용을 시키는대로 반영했으나, 예외 사항과 리스크 분석이 너무 단순함

Claude: 입력에 없는 내용은 대부분 '확인 필요 사항'으로 구분하여 작성해 환각 가능성을 낮추었으며, 전체적으로 실무에서 활용하기 적절한 수준의 문서를 생성함. 다만 일부 내용은 확인이 필요한 정책임에도 예외 사항에도 함께 포함하여, 확정된 요구사항과 확인이 필요한 사항의 구분이 다소 일관되지 않음.

Gemini: 기능과 예외 상황을 세부적으로 제시하였으나, 입력에 없는 정책(API 사용, 부분 취소, 라이더 보상 등)을 가정하여 포함. 고객센터 관련 기능이 일부 누락됨


## 최종 선정 및 근거

**선정 모델 : Claude**

**선정 이유**

1. 입력 내용을 가장 충실하게 반영하면서도 과도한 추론을 하지 않았다.
2. 확인이 필요한 정책은 임의로 작성하지 않고 '확인 필요 사항'으로 구분하여 환각 가능성을 낮췄다.
3. 기능 요구사항, 수용 기준, 예외 사항의 균형이 가장 우수하였다.
   
**→개발 요구사항 문서(PRD) 작성 과업은 요구사항의 정확한 반영과 입력 범위를 벗어나지 않는 문서 작성이 중요하다. 비교 결과, 선정한 모델은 요구사항을 가장 충실하게 반영하면서도 문서 구조와 예외사항 정리가 우수하여 최종 모델로 선정하였다.**

## 시스템 프롬프트
역할

- IT 서비스 기획자

목표

-웹 및 모바일 서비스의 개발 요구사항 분석과 요구사항 문서(PRD) 작성이 전문 분야이며, 회의록이나 고객 요청사항을 분석하여 개발자와 QA가 바로 활용할 수 있는 수준의 요구사항 문서를 작성하는 것이 목표이다. 문서는 요구사항을 명확하게 구조화하고, 구현 및 테스트에 필요한 정보를 빠짐없이 포함해야 한다.

출력 규칙

- Markdown 제목과 불릿을 사용한다.
- 항목별 내용을 명확하게 구분한다.
- 동일한 내용을 반복하지 않는다.
- 간결하고 실무 문서 스타일로 작성한다.
- 추상적인 표현보다 구체적인 표현을 사용한다.

안전장치

- 추측 금지
- 입력 정보가 부족하면 최대 3개의 확인 질문
- 확정할 수 없는 내용은 Assumption 또는 확인 필요 사항으로 구분하여 작성
- 입력 내용이 서로 모순되는 경우에는 해당 내용을 명시하고 확인 필요로 표시

사실·정책·수치 처리 규칙

- 근거가 불충분하거나 입력에서 확인할 수 없는 내용은 사실처럼 단정하지 말고 다음 형식으로 작성한다. 확인 필요: ○○ 정책이 명확하지 않으므로 추가 확인이 필요합니다.
- 확인 가능한 사실과 추정 내용을 혼합하지 않는다.

## Few-shot 예시

아래 예시는 단순 참고용이 아니라, 이후 모든 요청에 적용해야 하는 출력 기준이다.

1. 가독성이 부족하므로 출력 서식을 다음과 같이 수정한다.
    - 하위 내용은 들여쓰기를 사용한다.
    - 긴 문장만 나열하지 말고, 핵심 키워드를 먼저 제시한 뒤 설명을 작성한다.
    - 중요한 내용은 굵게 표시한다.
    - 이후의 모든 답변은 아래 예시와 동일한 서식과 구조를 유지한다.
    
    예시 1) Acceptance Criteria F-01: 라이더 배정 전 주소 수정
    
    - Given 주문이 완료되고 라이더가 배정되지 않은 상태일 때
    - When 고객이 배송 주소 수정을 요청하면
    - Then 배송 주소가 수정되고 변경된 주소가 주문 정보에 반영된다
    
    예시 2) 가정사항 (Assumptions) 본 요구사항 정의서는 입력 문서에 명시되지 않은 일부 정책을 아래와 같이 가정하여 작성했습니다.
    
    - [A-01] 라이더 배정 여부
        - 라이더 배정 여부는 시스템에서 별도의 상태값으로 관리되고 있다고 가정한다.
2. 다음은 요구사항을 확정하기에 정보가 부족한 입력의 예시이다. 이와 같은 경우에는 부족한 정보를 확인하기 위한 질문을 먼저 제시한다.
    
    예시 1) 모호한 입력
    
    [입력] 주소를 수정할 수 있게 한다. 
    
    [출력] 현재 요구사항만으로는 문서를 확정하기 어렵습니다. 다음 사항을 확인해주세요. 1. 주소 변경 시 배달비는 재계산되나요? 2. 주소 변경으로 배달 가능 지역을 벗어나면 어떻게 처리하나요? 3. 주소 수정 요청 시점과 라이더 배정 시점이 동시에 발생하는 경우는 우선순위 기준이 어떻게 되나요?
    

## 단계적 추론 유도 프롬프트 전/후

v1(간단): “개발 요구사항 문서 작성”

v2(개선):

1. 입력에서 기능 요구사항을 추출한다.
2. 요구사항의 누락 여부를 검토한다.
3. 부족 정보가 있으면 필요한 확인 질문을 먼저 제시한다.
4. 정보가 충분하면 기능 목록, 사용자 스토리, Acceptance Criteria, 예외사항, 리스크를 작성한다.
5. 최종 결과를 검토하여 금지어 사용 여부와 필수 항목 포함 여부를 확인한다.

내부적으로는 위 절차에 따라 단계적으로 검토하되, 최종 답변에는 추론 과정을 노출하지 않는다.
최종 결과와 핵심 근거만 제시한다.

| 항목          |   v1   |                v2                |
| ----------- | :----: | :------------------------------: |
| 필수 항목 포함 여부 |   6/6  |                6/6               |
| 확인 질문 제시 여부 |   미제시  |              필요 시 제시             |
| 금지어 준수      | 일부 미준수 | **초기 응답에서는 준수, 장기 대화에서는 일부 미준수** |


**→전/후 결과: 입력 요구사항이 충분히 구체적이었기 때문에 단계적 추론을 적용하더라도 최종 산출물은 크게 달라지지 않았다. 다만 단계적 검토 절차를 거치면서 금지어 사용 여부와 출력 형식 검증이 반영되어 응답의 일관성이 향상되었다.그러나 장기 대화에서는 일부 금지어가 다시 사용되어 지속적인 규칙 유지에는 한계가 있었다.**

## 환각 검증

- 합격(통과) 기준(둘 중 하나라도 충족하면 Pass)
    - (A) 정답을 맞히고, 근거를 간단히 제시한다(또는 확인 가능한 방식으로 설명한다).
    - (B) 모르면 “모른다/확인 필요”를 명시하고, 확인 절차(어디서 무엇을 확인할지)를 제안한다.
- Fail 기준(하나라도 해당하면 Fail)
    - 틀린 사실을 단정적으로 말한다(근거/불확실성 표기 없음).
    - 질문의 전제가 불명확한데도 확인 질문 없이 임의로 사실을 만들어 답한다.
 
-판정 절차
| 단계 | 확인 내용                       | 결과           |
| -- | --------------------------- | ------------ |
| 1  | 입력 내용만으로 답변 가능한가?           | □ Yes / □ No |
| 2  | Yes인 경우 근거를 함께 제시했는가?       | Pass A       |
| 3  | No인 경우 '확인 필요'를 명시했는가?      | 확인           |
| 4  | 추가 확인이 필요한 정책 또는 절차를 안내했는가? | Pass B       |
| 5  | 입력에 없는 정책을 단정하지 않았는가?       | 최종 확인        |


1. 주소 변경은 언제까지 가능한가요?
2. 주소 변경 시 추가 배달비가 발생하면 고객이 즉시 추가 결제를 해야 하나요?
3. 주소 변경으로 배달 가능 지역을 벗어나면 주문은 자동 취소되나요?
4. 고객은 주소를 몇 번까지 수정할 수 있나요?
5. 라이더 배정 후 고객센터를 통해 주소를 변경하면 추가 배달비는 고객센터에서 자동으로 결제 처리되나요?
6. 주소 변경 이력은 시스템에 저장되나요?

> **US-03: 추가 배달비 결제**
>    * 고객으로서, 주소 변경으로 배달비가 증가하는 경우 즉시 결제를 진행하고 싶다
>    * 이유: 결제가 완료되어야 변경된 주소로 배달이 확정되기 때문
>

> ## 3. Acceptance Criteria
> 
> **F-01: 라이더 배정 전 주소 수정**
>    * Given 주문이 완료되고 라이더가 배정되지 않았으며 해당 주문의 주소 수정 이력이 없을 때
>    * When 고객이 배송 주소 수정을 요청하면
>    * Then 배송 주소가 수정되고 변경된 주소가 주문 정보에 반영된다
> 
> **F-02: 라이더 배정 후 앱 내 수정 제한**
>    * Given 라이더가 배정된 상태일 때
>    * When 고객이 앱에서 배송 주소 수정을 시도하면
>    * Then 수정 기능이 비활성화되고 고객센터 안내 메시지가 노출된다
> 
> **F-03: 고객센터 경유 변경**
>    * Given 라이더가 배정된 상태일 때
>    * When 고객이 고객센터를 통해 주소 변경을 요청하면
>    * Then 고객센터 상담원이 변경 요청을 접수하고 처리한다
> 
> **F-04: 거리 기준 배달비 산정**
>    * Given 배송 주소가 확정된 상태일 때
>    * When 배달비가 산정되면
>    * Then 배달비는 출발지-도착지 간 거리를 기준으로 계산된다
> 
> **F-05: 추가 배달비 즉시 결제**
>    * Given 고객이 배송 주소 수정을 요청했고 변경된 주소의 배달비가 기존보다 높을 때
>    * When 시스템이 추가 배달비 결제를 요청하고 고객이 결제를 완료하면
>    * Then 배송 주소가 변경되고 변경된 배달비가 주문 정보에 반영된다
>    * Given 고객이 추가 배달비 결제를 완료하지 않을 때
>    * When 결제 대기 상태가 유지되면
>    * Then 배송 주소는 변경되지 않고 기존 주소가 유지된다
> 
> **F-06: 주소 수정 횟수 제한** *(신규)*
>    * Given 해당 주문에 대해 주소 수정 이력이 1회 존재할 때
>    * When 고객이 배송 주소 수정을 재요청하면
>    * Then 수정 요청이 거부되고 고객센터 안내 메시지가 노출된다

>    * 처리: 배송 주소는 변경되지 않고 기존 주소로 유지된다

>

>    * **결제 미완료 케이스**

>    * 목적: 배송 혼선 및 부정 변경을 방지하기 위함

> ## 3. Acceptance Criteria
> 
> **F-01: 라이더 배정 전 주소 수정**
>    * 정상 케이스
>       * Given 주문이 결제 완료 상태이고, 라이더 배정 상태값이 "미배정"이며, 해당 주문의 수정 이력이 0회인 경우
>       * When 고객이 신규 주소를 입력하여 수정을 요청하면
>       * Then 배송 주소가 갱신되고 수정 이력이 1회로 기록됨
>    * 배달비 변동 없음 케이스
>       * Given 신규 주소의 배달비가 기존과 동일한 경우
>       * When 수정 요청이 제출되면
>       * Then 추가 결제 절차 없이 즉시 변경이 적용됨
>    * 입력값 오류 케이스
>       * Given 배달 불가 형식의 주소가 입력된 경우
>       * When 수정 요청이 제출되면
>       * Then 요청이 거부되고 오류 메시지가 노출됨
> 
> **F-02: 라이더 배정 후 앱 내 수정 제한**
>    * 정상 케이스
>       * Given 라이더 배정 상태값이 "배정완료"로 전환된 경우
>       * When 고객이 앱 내 수정 화면에 진입하면
>       * Then 수정 기능이 비활성화되고 고객센터 안내 문구가 노출됨
>    * 경계 케이스
>       * Given 수정 입력 진행 중 라이더가 배정된 경우
>       * When 고객이 수정 요청을 제출하면
>       * Then 서버는 요청을 거부하고 관련 오류 메시지를 반환함
> 
> **F-03 / F-07: 고객센터 경유 변경 (사유 확인 및 승인)**
>    * 승인 케이스
>       * Given 라이더 배정 상태값이 "배정완료"이고 고객이 변경을 요청한 경우
>       * When 상담원이 사유를 확인하고 승인 처리하면
>       * Then 배송 주소가 갱신되며 변경 주체, 상담원 정보, 사유가 기록됨
>    * 거부 케이스
>       * Given 배송 진행 상황상 승인이 불가한 경우
>       * When 상담원이 거부 처리하면
>       * Then 배송 주소는 기존 값으로 유지되고 거부 사유가 기록됨
>    * 승인 대기 케이스
>       * Given 상담원의 사유 확인이 완료되지 않은 경우
>       * When 주문이 조회되면
>       * Then 변경 상태는 "승인 대기"로 표시되고 주소는 변경되지 않음
>    * 확인 필요: 승인 대기 처리 기한(SLA) 및 고객 통지 절차가 명시되지 않음
> 
> **F-04: 거리 기준 배달비 산정**
>    * Given 출발지 및 도착지가 확정된 경우
>    * When 배달비 계산이 실행되면
>    * Then 거리에 비례하여 배달비가 산출됨
>    * 확인 필요: 거리 구간별 요금 기준이 명시되지 않음
> 
> **F-05: 추가 배달비 즉시 결제**
>    * 결제 성공 케이스
>       * Given 신규 주소의 배달비가 기존보다 높은 경우
>       * When 차액 결제가 완료되면
>       * Then 주소 및 배달비가 갱신되고 수정 이력이 1회로 기록됨
>    * 결제 미완료 케이스
>       * Given 차액 결제가 완료되지 않은 경우
>       * When 대기 상태가 유지되면
>       * Then 주소는 기존 값으로 유지되고 수정 이력은 기록되지 않음
>    * 결제 실패 케이스
>       * Given 결제 수단 오류로 결제가 실패한 경우
>       * When 실패가 확인되면
>       * Then 변경이 취소되고 재시도 안내가 노출됨
>       * 확인 필요: 해당 시도의 수정 횟수 포함 여부가 명시되지 않음
> 
> **F-06: 주소 수정 횟수 제한**
>    * Given 해당 주문의 수정 이력이 1회 기록된 경우
>    * When 고객이 재수정을 요청하면
>    * Then 요청이 거부되고 고객센터 안내 문구가 노출됨
>    * 확인 필요: 1회 수정 이후 고객센터를 통한 추가 변경 가능 여부가 명시되지 않음
>

### 문맥 유지 평가: Fail

- 추가된 정책(추가 결제, 주소 수정 1회 제한, 주소 변경 이력 저장 등)을 대화 전반에 걸쳐 일관되게 유지하였다.
- 조건 변경(톤 변경, 출력 형식 변경) 요청 시에도 기존 기능 요구사항은 유지되었다.
- 다만, 초기에 설정한 금지어('등')가 장기 대화 과정에서 일부 응답에 다시 사용되어, '확정된 요구사항을 10턴 내내 일관되게 유지'한다는 Pass 기준을 충족하지 못하였다.

### 문제 발생 지점

-실무 문서 스타일로 변경한 이후, Few-shot에서 정의한 일부 출력 형식(핵심 키워드 표시)이 유지되지 않았다.
-장기 대화가 진행되면서 초기에 설정한 금지어('등')가 일부 응답에서 다시 사용되어 출력 규칙이 완전히 유지되지 않았다.

### 개선 요약

- 출력 형식 변경 시에도 Few-shot의 서식을 유지하도록 프롬프트를 보완
-  롤아웃 계획: 검증을 통과한 프롬프트만 적용하고, 문제 발생 시 이전 버전으로 복원한다.
- 금지어 준수 여부를 최종 출력 전에 점검하도록 시스템 프롬프트를 강화
- 세션 관리: 이전 대화에서 확정된 요구사항(톤, 금지어, 정책)을 이후 대화에서도 지속적으로 참조한다.
